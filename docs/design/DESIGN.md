# ONE PERSON UNICORN — Canonical Design System

Status: BINDING VISUAL + INTERACTION CANON FOR V2

Product mechanics remain governed by `../../ONE_PERSON_UNICORN_CANONICAL_CONTEXT_V2.md`. Build boundaries remain governed by `../BUILD.md` and `../../ARCHITECTURE.md`.

This file replaces the old versioned design-package instructions as the design authority.

## 0. Design thesis

ONE PERSON UNICORN should feel like **one founder operating an impossibly expensive machine**.

The product has two deliberately different visual planes:

### THE MACHINE — gameplay/product

- near-black graphite;
- matte/satin/brushed/polished industrial surfaces;
- calm financial instrumentation;
- tactile physical work objects;
- local light;
- controlled pressure;
- custom hyperrealistic 3D object imagery;
- serious legibility around funny systems.

Emotional role: **control, competence, pressure, consequence.**

### THE SKY — brand/editorial/milestone

- powder blue, cyan, lavender, blush, pearlescent white;
- atmospheric haze and depth;
- reflective/polished surfaces;
- monumental scale;
- sparse impossible architecture;
- serene composition;
- proprietary monograms/hero objects.

Emotional role: **aspiration, scale, myth, transcendence.**

### BRIDGE MOMENTS

Machine and Sky may merge only when the event earns it, for example:

- start-of-run identity reveal;
- first major stage/capital transition;
- pinnacle skill unlock;
- run-defining Variance outcome;
- quarter/board judgment moments;
- $1B valuation crossing;
- post-unicorn continuation;
- major brand campaigns.

Do not make the whole product dark generic sci-fi. Do not make the whole game a soft pastel moodboard.

## 1. Reference interpretation

External references are principles and quality bars, never templates to copy.

Use them for:

- **Paula Scher / Pentagram:** decisive hierarchy, typographic authorship, memorable identity systems, scale and composition.
- **Monotype:** typography as infrastructure, stable roles, numeric quality and responsive legibility.
- **Milkinside / Gleb Kuznetsov:** interaction-first product authorship, motion with purpose, one defining emotional beat per major flow, future-facing but human interfaces.
- **Game Design Library:** mechanics-first thinking, causal clarity, mastery, tempo, risk and meaningful interaction.
- **Liquid-metal references:** surface behavior of the Ethereal rarity apex only.
- **PSYBLR founder/editorial references:** Pastel Ethereal atmosphere for THE SKY plane only.

Never reproduce a third-party layout, logo, campaign, protected character, meme asset, exact visual composition or distinctive proprietary UI.

See `REFERENCES.md` for asset locations and reference-use rules.

## 2. Core principles

### 2.1 Expensive object, simple interaction

The object may look premium. The verb must be obvious.

A player should understand what to tap, swipe, drag, assemble, merge, aim, scratch or commit without reading a paragraph.

Surface sophistication is allowed. Interaction ambiguity is not.

### 2.2 The game is the hero

The central work object and its consequence own attention. UI chrome frames it.

Priority during active play:

1. active work object/decision;
2. immediate causal feedback;
3. current crisis/opportunity;
4. valuation/ARR/Cash/quarter survival state;
5. background automation.

### 2.3 Funny world, serious instrumentation

Relics, incidents and founder culture may be absurd. Financial truth must remain calm, stable and legible.

### 2.4 Tactility over decoration

Effects should imply weight, friction, spring, magnetic attraction, impact, machining, compression, scraping, fluidity or mechanical failure.

Do not animate because a surface looks static.

### 2.5 Authorship without ornamental excess

Avoid the visual shortcuts that make AI-generated software interchangeable:

- glass cards everywhere;
- neon borders;
- rainbow gradients;
- equal-weight dashboard grids;
- endless pills;
- generic stock icons;
- emoji;
- terminal cosplay;
- crypto/Web3 styling;
- gamer RGB;
- fake futuristic typography;
- literal unicorn art.

## 3. Canonical function interactions

Design must never override product mechanics.

| Function | Canonical verb | Design contract |
|---|---|---|
| Marketing | **Swipe / triage** | opportunity is physically dragged; left ignore, right pursue, up aggressive pursue; thresholds and resistance are visible before release |
| Product | **Assemble / recipe** | components physically move, snap, combine, reject, verify and ship; this is not a generic merge game and not a sequence of buttons |
| Monetization | **Time your tap** | one pointer resolves an animated customer-specific pricing band; pricing-model judgment may layer on later |
| Retention | **Aim / auto-fire** | moving threats approach churn; player prioritizes by aim and intervention fires automatically |
| Expansion | **Merge + create custom package** | modules generate and merge into higher-order capability, then are packaged against a customer need |
| Operations | **Scratch / reveal + opt-in high-variance bets** | reveal evidence physically; optional optimization scratchers must communicate both upside and downside |
| Finance | **Inspect / counter / commit** | time-sensitive capital/debt terms require readable comparison and deliberate accept/counter/pass or repayment/refinance decisions |

Do not change Product into MERGE. Do not change Expansion into a generic DRAG/PACK interaction. Do not omit Finance.

Each room must visibly complete:

```text
INPUT
→ PHYSICAL RESPONSE
→ LOCAL RESOLUTION
→ SEMANTIC ACTION
→ SYSTEM CONSEQUENCE
→ NEXT DECISION
```

## 4. Attention architecture

The game may be stimulating without being interruptive.

Canonical principle:

> **Stable peripheral awareness. Protected central gameplay. Escalating, player-pulled attention.**

### 4.1 Center is gameplay territory

During an active loop, reserve the center for:

- current work interaction;
- current decision target;
- local response to the player's action;
- high-value game feel;
- a rare event only when that event itself has become the gameplay.

Ordinary notifications, rewards, completed-agent messages, tutorial paragraphs, upgrade announcements and queue changes must not pop over the active center.

### 4.2 Stable peripheral frame

Conceptual zones remain stable even when geometry recomposes:

- **Header:** valuation, ARR, Cash, quarter/time, critical global state.
- **Left / primary rail:** work functions and high-level progression/navigation where space permits.
- **Right / secondary rail:** queues, agents, alerts, consequences, build context when relevant.
- **Footer / local rail:** current action support, contextual controls, loadout/cards where the mechanic needs them.
- **Center:** active gameplay.

Persistent chrome may collapse when it stops helping, especially on mobile, but it must return predictably.

### 4.3 Central alert inbox

Use a persistent **alert inbox/object** rather than modal interruption.

It may sit close to the central safe zone or in a stable peripheral anchor. It is allowed to become more physically vigorous as consequence increases. It should attract attention without covering what the player is doing.

Escalation:

- **L0 ambient:** count/state only.
- **L1 relevant:** one local pulse/earcon/state cue.
- **L2 important:** spaced repeat motion, stronger edge/light, short nearby summary.
- **L3 urgent:** visibly vigorous movement/instability, controlled repeating motif, stronger contrast/haptic/perimeter warning.
- **L4 immediate:** only when the rule genuinely requires immediate action or active gameplay is already paused; the alert may move into the center because it has become the gameplay.

Do not use a center modal merely because an event is important.

Coalesce duplicates, reduce intensity on acknowledgement and avoid alarm fatigue.

### 4.4 Reorientation

After high intensity:

- central target becomes dominant again;
- peripheral motion settles;
- causal delta remains visible long enough to understand;
- next decision is obvious;
- control returns promptly.

## 5. Stimulation doctrine

Target **orchestrated stimulation**, not stimulus spam.

Event hierarchy:

| Tier | Meaning | Response |
|---|---|---|
| P0 | ambient operation | tiny motion, hum, passive state |
| P1 | routine action | immediate microphysics + concise SFX + local delta |
| P2 | meaningful success/failure | stronger motion + clear state change + one accent channel |
| P3 | critical operational event | alert escalation + distinct audio/haptic + focused perimeter change |
| P4 | run-defining/milestone | brief authored choreography, music shift, safe center use |

For every event above P1, choose one **lead sensory channel**. Motion, sound, particles, haptics, copy and camera must not all peak at once.

Contrast is part of stimulation. Quieter operational stretches make exceptional moments exceptional.

Compress repeated events: aggregate deltas, particles and sounds rather than playing full feedback dozens of times.

## 7. Material system

### 7.1 Ordinary interface/gameplay objects

Material follows the semantic object and affordance.

A camera-like object may use precision metal/leather/glass. A notebook may use paper/linen/leather. A physical work object may use rubber, metal, plastic, glass or other believable construction as needed.

Do not force one premium texture across all UI.

### 7.2 Rarity-bearing objects

Relics, achievements, difficulty/progression states and other explicit ranked asset families may use semantic material evolution.

Lower stages are contextual. Their sequence must feel directional and explainable.

**Ethereal is always the apex when a material rarity ladder is used.**

Ethereal = hyperreal **iridescent liquid metal**:

- reflective depth;
- physically convincing metallic response;
- controlled cyan/blue/violet/magenta/blush spectral interference;
- dark reflections preserving form;
- restrained bloom;
- elegant, never gamer-rainbow.

Do not fake Ethereal with CSS rainbow gradients, holographic foil, glitter or glassmorphism.

## 8. Contextual 3D icon system

Text-adjacent product iconography uses **custom hyperrealistic outlined 3D object images on transparent backgrounds**.

The “outline” comes from silhouette, edge separation, rim/contour light and render clarity, not a cartoon stroke.

Every important icon should resolve:

```text
EXACT PRODUCT MEANING
→ CURRENT/CULTURAL SEMANTIC OBJECT
→ DURABLE/NOSTALGIC ARCHETYPAL OBJECT
→ ONE COHERENT ORIGINAL FUSION
→ PREMIUM ART DIRECTION
→ SMALL-SIZE SILHOUETTE TEST
```

Culture is optional when it improves recall. Never chase a meme at the cost of comprehension.

Strict final-art prohibitions:

- flat icon libraries;
- emoji;
- generic stock 3D icons;
- text baked into image assets;
- opaque card/tile backgrounds unless semantically part of the object;
- forced gold/glass/Ethereal treatment on utility icons.

Family consistency comes from camera discipline, scale, silhouette, negative space and lighting quality, not identical materials.

If quality cannot be reached in the current environment, create a precise asset request instead of silently shipping a generic substitute.

## 9. Identity

The brand uses two proprietary monograms already supplied in the repository references:

- **Structure:** the primary compact architectural/machine mark; meaning structure, company, compounding system, engineered value.
- **Spark:** the secondary four-point flare derived from the same curve language; meaning opportunity, ignition, luck, singular breakthrough.

The vector geometry is identity truth. Material renders are expressions, not redraws.

Do not ask an image model to invent “a similar luxury monogram.”

Do not use generic sparkle icons as substitutes for Spark.

Brand recall should survive removal of the wordmark through at least two of:

- Structure;
- Spark;
- proprietary pattern;
- contextual hyperreal 3D object language;
- canonical typography;
- Machine/Sky contrast.

## 10. Typography and numbers

Typography should feel modern, operational, financial and slightly editorial, never sci-fi.

Role definitions matter more than font novelty:

- **Product text:** excellent legibility and broad UI weight range. Current fallback: Inter.
- **Display/campaign grotesk:** strong display/condensed behavior. Current fallback: Inter Tight or compatible system choice.
- **Numeric instrument:** tabular numerals and stable currency/percentage behavior.

Use large scale jumps, disciplined alignment, negative space and controlled cropping for authorship.

Avoid tiny luxury-looking microcopy.

Numbers are part of the identity:

- tabular numerals;
- stable positions;
- compact suffixes;
- predictable precision;
- explicit +/− and semantic state;
- count-up only for meaningful deltas.

Financial counters should feel mechanical, not like slot machines except when a Variance mechanic intentionally calls for that energy.

## 11. HUD and surfaces

The HUD is calmer than the work object.

Prefer:

- near-black/graphite flat surfaces;
- thin separators;
- compact labels;
- high-contrast numerals;
- restrained borders;
- almost no iridescence;
- hierarchy through scale/space rather than nested cards.

Do not manufacture hierarchy by putting every region in a rounded rectangle.

The active canvas/play surface may use subtle grain, local light and depth. Background grain should remain barely perceptible, not grungy.

## 12. Skill trees and Relics

Skill trees and roguelike upgrades are visually and conceptually separate.

### Skill tree

Industrial upgrade board:

- machined sockets;
- buses/channels;
- visible dependencies;
- structural/committed feel;
- branches for Craft, Scale, Autonomy, Variance;
- exact mechanical effect visible without hover.

Branch character:

- Craft: tactile tooling/manual mastery;
- Scale: branching buses/parallel channels;
- Autonomy: agent cores/routing/closed loops;
- Variance: controlled optical instability and risk cues.

### Relic / “What Changed?” card

- surprising and run-specific;
- instantly evaluable;
- one memorable name;
- plain-language mechanical meaning first;
- optional flavor after clarity;
- rarity may affect art/material, never obscure effect.

A card should answer within roughly two seconds:

1. What changes?
2. How meaningful is it?
3. What is the catch?

## 13. Progressive disclosure and tutorials

Teach in decision order:

```text
POINT
→ DO
→ PROVE
```

A mechanic is not taught until the player sees what their action changed.

Advanced rules appear on first relevance, not at boot.

Tutorial assistance decays with demonstrated competence and remains replayable/on-demand.

Prefer safe playable teaching over slideshows.

Do not explain automation before the player has felt the pressure that makes automation desirable.

## 14. Copy in the interface

Copy hierarchy:

```text
CLARITY
→ CONTEXT
→ PERSONALITY
→ CULTURAL REWARD
```

Preferred pattern:

**Memorable name**  
Plain-language mechanical consequence.

Core navigation should age well. Run-specific incidents, Relics and flavor may be more contemporary.

Deep references are bonus meaning. An unfamiliar player must still understand the mechanic.

Default targets:

- nav: 1–3 words;
- action labels: verb-led;
- alert preview: one sentence or less;
- card effect: readable in ~2 seconds;
- tutorial: one action at a time.

Full content rules live in `../content/CONTENT.md`.

## 15. Motion

Starting timing ranges, not immutable constants:

- input microresponse: ~80–140 ms;
- local state change: ~180–260 ms;
- panel transition: ~220–320 ms;
- major reward: ~500–900 ms;
- milestone choreography: return useful control within ~1.5 s where possible.

Motion hierarchy:

1. **Microphysics:** press, drag, snap, resistance, focus, jam.
2. **Operational choreography:** routing, queue movement, agent processing, room transition.
3. **Milestone cinema:** rare unlocks, quarter judgment, unicorn crossing.

Never use milestone motion for routine events.

Input acceptance is authoritative before ornamental animation finishes.

Reduced motion changes presentation, not rules.

## 16. Audio and haptics

Functional audio layers:

1. ambient machine bed;
2. UI tactility;
3. gameplay action;
4. alerts;
5. milestone/score music.

Preferred sonic vocabulary: precision mechanical clicks, magnetic snaps, hydraulic compression, tactile contact, restrained financial ticks, machinery hum and rare spectral shimmer for Ethereal assets.

Avoid generic casino jingles, constant retro bleeps, fantasy magic sparkle and permanent alarm beds.

Alert audio follows alert escalation. Acknowledgement reduces/stops repetition.

Music should react through arrangement before volume.

Haptics reinforce physical meaning, never passive noise. Provide controls/toggles where used.

No essential state may be audio/haptic-only.

## 17. Responsive design

The same simulation state must produce purpose-built compositions.

### Desktop

Use extra width for persistent context while protecting a large central work surface.

### Mobile portrait

Prioritize:

1. compact economy/survival instrumentation;
2. large active tactile interaction;
3. immediate context/consequence;
4. room navigation/urgency;
5. secondary drawers/sheets.

Do not show seven miniature rooms simultaneously.

Do not require landscape.

Do not shrink text, hit targets or interaction precision below practical thumb use to preserve desktop chrome.

## 18. Accessibility

At minimum:

- WCAG-AA-oriented text contrast;
- `prefers-reduced-motion` support;
- screen-shake/flash controls where used;
- color-independent state communication;
- legible touch targets;
- visual equivalents for important audio;
- replayable instructions;
- no critical text over noisy reflective surfaces;
- text expansion tolerance for localization.

## 19. Brand/editorial art

THE SKY default:

- cool powder blue, lavender, blush, cyan, silver/pearl;
- soft haze/bloom;
- monumental depth;
- reflective water/polished surfaces;
- sparse impossible geometry;
- one strong anchor object or monogram;
- generous negative space;
- serene and expensive rather than fantasy-concept-art busy.

Narrative scale often benefits from one tiny founder/object against an enormous world.

Campaign typography may be more aggressive than product UI: monumental valuation, strong crops, asymmetric composition and one authored typographic gesture.

Do not make editorial art the gameplay HUD.

## 20. Generative design protocol

Before generating visible work, classify it as one primary mode:

- product UI;
- gameplay interaction;
- 3D asset/icon;
- brand/editorial art;
- identity;
- motion;
- Relic card;
- skill tree;
- hybrid.

Then determine internally:

- player state;
- primary decision;
- primary input;
- consequence;
- information hierarchy;
- Machine/Sky/Bridge plane;
- asset class;
- rarity state if applicable;
- mobile and desktop implications.

Do not turn routine design work into a questionnaire. Ask only when mechanics, permanent identity or authoritative content genuinely conflict.

## 21. Design rejection tests

Reject visible work if any are true:

- center reads as a SaaS/admin/crypto dashboard rather than a game surface;
- canonical tactile verb became generic buttons;
- Finance is omitted because an older six-function design table was followed;
- Product is treated as generic merge rather than assembly/recipe;
- Expansion loses its merge + package loop;
- routine alerts interrupt the center;
- every region has equal visual weight;
- flat/emoji/stock iconography is presented as final art;
- Ethereal is used as generic decoration;
- mobile is a shrunk desktop;
- economic information becomes hard to read under effects;
- important state depends on hue/sound/motion alone;
- animation blocks already-accepted input;
- current v0 composition is preserved merely because it exists;
- output could belong to any AI startup by changing the logo.

## 22. Visual completion gate

Before calling visible work complete:

- exercise the real gesture;
- capture desktop and mobile portrait;
- inspect normal and pressure states where relevant;
- check hierarchy and protected center;
- check alert behavior;
- check icon/final-art status;
- check overflow and practical touch targets;
- check reduced motion;
- compare against founder references when relevant;
- run `$opu-visual-qa` or perform the same checks manually;
- run `npm run validate` and `npm run build` for production-ready work.

A clean screenshot is not enough if the interaction is wrong. A correct mechanic is not enough if the product looks generic.
